#                                                                              #
#  SECTION 1 — EXECUTIVE SUMMARY                                               #
#                                                                              #
################################################################################

UniAttend is a full-stack university attendance management system with two
distinct user portals:

  ┌─────────────────────────────────────────────────────────────────────┐
  │ ADMIN PORTAL                                                        │
  │   - Manage departments (CS, EE, BBA, ...)                          │
  │   - Manage sections within each department/year                    │
  │   - Manage students (manual + bulk Excel/CSV import)              │
  │   - Manage teachers (auto-generated 6-digit IDs + passwords)      │
  │   - Manage subjects (dept-specific, with credit hours)            │
  │   - Assign teachers to subjects in sections                       │
  │   - View attendance records across all sections                   │
  │   - Export attendance as Excel/PNG (per student, per section)     │
  │   - Reset teacher passwords via Edge Function                     │
  └─────────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────────┐
  │ TEACHER PORTAL                                                      │
  │   - Log in with 6-digit ID + password                             │
  │   - See only assigned classes (subject + section)                 │
  │   - Mark attendance: present/absent per student                   │
  │   - Support for 1-slot and 2-slot (combined) classes              │
  │   - View attendance summary: per-student %, attended / conducted  │
  │   - Credit-hour cap prevents over-marking (credit_hours × 15)     │
  │   - One class per subject per section per day                     │
  └─────────────────────────────────────────────────────────────────────┘

Key design decisions:
  • Synthetic emails: <6-digit-id>@uniattend.app used as Supabase Auth emails
    because Auth requires email format but teachers never see it
  • Denormalized fields: teacher_name, subject_name copied into assignment
    and session tables for fast reads + historical accuracy
  • RPCs for atomic operations: mark_attendance, increment_section_students,
    get_attendance_summary, get_section_attendance_report
  • Row Level Security (RLS) on every table with auth_read + auth_write policies
  • Feature-first folder structure (models / screens / services / providers)
  • All Firebase references removed; fully migrated to Supabase

Data flow example — Teacher marks attendance:
  1. Teacher taps Submit on Mark Attendance screen
  2. AttendanceService.markAttendance() called
  3. supabase.rpc('mark_attendance', params: {...})
  4. RPC validates:
     - Not already marked today for this subject+section
     - Slot cap not exceeded (credit_hours × 15)
  5. RPC inserts:
     - 1 row in attendance_sessions
     - N rows in attendance_records (one per student)
  6. Session ID returned to client
  7. Client shows success, pops back

#  SECTION 5 — DATABASE SCHEMA (SUPABASE)                                      #
#                                                                              #
################################################################################

9 tables + 1 audit-friendly design:

  ┌────────────────────────────────────────────────────────────────────────────┐
  │ departments                                                                │
  │   id (text PK)  |  name (text)  |  is_active (bool)  |  created_at (ts)    │
  └────────────────────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────────────────────┐
  │ teachers                                                                   │
  │   id (text PK = auth UID)  |  login_code (unique)  |  full_name           │
  │   contact_email  |  auth_email  |  role  |  is_active                     │
  │   has_changed_password (bool)  |  created_at                              │
  └────────────────────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────────────────────┐
  │ admins                                                                     │
  │   id (text PK = auth UID)  |  full_name  |  email  |  role  |  is_active   │
  │   created_at                                                              │
  └────────────────────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────────────────────┐
  │ sections                                                                   │
  │   id (text PK) = "CS-3A"  |  department_id FK  |  year  |  name           │
  │   academic_year  |  total_students  |  is_active  |  created_at          │
  └────────────────────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────────────────────┐
  │ students                                                                   │
  │   id (uuid PK)  |  full_name  |  roll_no  |  enrollment_id                │
  │   department_id FK  |  section_id FK  |  year  |  is_active  |  created_at│
  │   UNIQUE(section_id, roll_no)                                             │
  └────────────────────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────────────────────┐
  │ subjects                                                                   │
  │   id (text PK) = "CS301"  |  name  |  credit_hours  |  department_id FK   │
  │   year  |  semester  |  is_active  |  created_at                          │
  └────────────────────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────────────────────┐
  │ teaching_assignments                                                       │
  │   id (uuid PK)  |  teacher_id FK  |  teacher_name (denorm)                │
  │   subject_id FK  |  subject_name (denorm)  |  section_id FK               │
  │   academic_year  |  semester  |  created_at                               │
  │   UNIQUE(subject_id, section_id) — one teacher per subject per section    │
  └────────────────────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────────────────────┐
  │ attendance_sessions                                                        │
  │   id (uuid PK)  |  subject_id FK  |  subject_name (denorm)                │
  │   section_id FK  |  teacher_id FK  |  teacher_name (denorm)               │
  │   date (date)  |  slot (text)  |  slot_count (int 1 or 2)                 │
  │   start_time  |  end_time                                                 │
  │   total_students  |  present_count  |  absent_count  |  status            │
  │   created_at                                                              │
  │   UNIQUE(subject_id, section_id, date)                                    │
  └────────────────────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────────────────────┐
  │ attendance_records                                                         │
  │   id (uuid PK)  |  session_id FK  |  student_id FK                        │
  │   student_name (denorm)  |  roll_no (denorm)  |  status                   │
  │   remarks  |  marked_at                                                   │
  │   UNIQUE(session_id, student_id)                                          │
  └────────────────────────────────────────────────────────────────────────────┘

RLS Policies:
  • Every table: auth_read for SELECT to authenticated
  • Every table: auth_write for INSERT/UPDATE/DELETE to authenticated
  • NOTE: Currently too permissive — any teacher can write anywhere.
          Tightening is in the Security Roadmap (Section 12).

RPC Functions:
  • increment_section_students(p_section_id, p_delta)
  • mark_attendance(...) — atomic session + records insert
  • get_attendance_summary(p_subject_id, p_section_id)
  • get_section_attendance_report(p_section_id)
  • get_student_attendance_breakdown(p_student_id, p_section_id)

Triggers:
  • trg_auto_confirm_users on auth.users — auto-confirms new signups

Edge Functions:
  • reset-teacher-password (Deno, uses Admin SDK)

This section is a detailed plan for making UniAttend production-grade secure.
Each item includes: why it matters, how to implement, and where to add code.

────────────────────────────────────────────────────────────────────────────────
 12.1 — SESSION MANAGEMENT
────────────────────────────────────────────────────────────────────────────────

  [S1] Session Timeout (Idle)
    Why   : If a teacher leaves their phone unattended, an attacker could
            mark bogus attendance.
    How   :
      1. Add lib/core/session_manager.dart
      2. Track last user activity via a global WidgetsBindingObserver
      3. On app resume / foreground, compare now vs lastActivity
      4. If > N minutes (configurable, e.g., 15 min for teachers,
         5 min for admins), force logout + redirect to login
      5. Reset timer on any user interaction (tap, keyboard)
    Code outline:
      class SessionManager {
        static const idleTimeoutTeacher = Duration(minutes: 15);
        static const idleTimeoutAdmin   = Duration(minutes: 5);
        DateTime _lastActivity = DateTime.now();
        void touch() => _lastActivity = DateTime.now();
        Future<bool> checkTimeout(String role) async {
          final limit = role == 'admin' ? idleTimeoutAdmin : idleTimeoutTeacher;
          if (DateTime.now().difference(_lastActivity) > limit) {
            await Supabase.instance.client.auth.signOut();
            return true; // timed out
          }
          return false;
        }
      }
      Wrap the app in a GestureDetector + Listener to call touch() on
      any user interaction.

  [S2] Absolute Session Timeout
    Why   : Even with activity, sessions shouldn't last forever.
    How   : Store login timestamp. Force re-auth after 12 hours (teachers)
            or 4 hours (admins), regardless of activity.

  [S3] Concurrent Session Limit
    Why   : Prevent account sharing (one teacher login used by 5 people).
    How   : Store active session IDs in a sessions table; on new login,
            either kick the old session or reject new login if > 2 active.
    Note  : Requires Edge Function for session tracking (Supabase Auth
            does not support this natively on free tier).

  [S4] Session Invalidation on Password Change
    Why   : If admin resets a teacher's password, all existing sessions
            must be terminated.
    How   : Supabase Auth auto-invalidates all sessions when
            updateUser({password}) is called via Admin API (already
            happens in reset-teacher-password Edge Function).
            Just add a UI notice telling the user they'll be logged out.

────────────────────────────────────────────────────────────────────────────────
 12.2 — AUTHENTICATION HARDENING
────────────────────────────────────────────────────────────────────────────────

  [A1] Brute Force Protection on Login
    Why   : Currently, an attacker can try infinite passwords.
    How   :
      1. Create table: login_attempts (id, login_code, ip, attempted_at)
      2. Before login, call an RPC `check_login_attempts(login_code)`:
         - Count attempts in last 15 min
         - If > 5 → reject with "Too many attempts. Try again in 15 min."
      3. After failed login, call RPC `record_login_attempt(login_code)`
      4. Successful login → RPC `clear_login_attempts(login_code)`
    Code outline (SQL):
      CREATE TABLE login_attempts (
        id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
        login_code text NOT NULL,
        attempted_at timestamptz DEFAULT now()
      );
      CREATE INDEX idx_login_attempts ON login_attempts(login_code, attempted_at);

  [A2] Password Strength Requirements
    Why   : Currently server-generated passwords are fine, but teachers
            change them later. Weak passwords = weak security.
    How   : In ChangePasswordScreen, validate:
      - Minimum 10 characters
      - At least 1 uppercase, 1 lowercase, 1 digit, 1 symbol
      - Not in a common-password dictionary (HIBP API on Pro plan;
        on free tier, bundle a small list of top-1000 passwords)

  [A3] Two-Factor Authentication for Admins
    Why   : Admin accounts are highest-value targets — one compromised
            admin can delete everything.
    How   : Supabase supports MFA (TOTP) natively.
      - In admin login, after email/password success, check if MFA is
        enrolled
      - If not, prompt enrollment: show QR code (use qr_flutter)
      - If enrolled, prompt TOTP code
      - Use supabase.auth.mfa.challenge() + verify()
    Note  : MFA is available on Free tier.

  [A4] Password Reset via Email (Real)
    Why   : Currently only admin can reset teacher passwords.
            Self-service is expected.
    How   : Set up Resend / Brevo (free tier: 3000 / 300 emails per day)
      - Supabase Dashboard → Auth → SMTP Settings
      - Enable "Reset password" email template
      - Add "Forgot Password?" link on login screen
      - Call supabase.auth.resetPasswordForEmail(email)

  [A5] Login Audit Trail
    Why   : Know when each account was last used, from where.
    How   : Add table login_audit (id, user_id, ip, user_agent, at, success)
            Populate via Edge Function that wraps login flow.
            Show last 5 logins on teacher/admin profile screen.

  [A6] Account Lockout After N Failed Attempts
    Why   : Stronger than rate limit — locks account entirely.
    How   : Add column teachers.locked_until timestamptz
            If failed attempts > 10 in last hour → locked_until = now()+1h
            Login checks locked_until, denies if locked.
            Admin can manually unlock from teachers list.

────────────────────────────────────────────────────────────────────────────────
 12.3 — DATA SECURITY (RLS TIGHTENING)
────────────────────────────────────────────────────────────────────────────────

  [D1] Restrict Writes by Role
    Why   : Right now every authenticated user can write to every table.
            A malicious teacher could delete all students via API.
    How   : Replace current policies with role-aware ones.
    Plan  :
      ┌────────────────────────┬──────────┬──────────┬──────────┐
      │ Table                  │ SELECT   │ INSERT   │ UPDATE   │
      ├────────────────────────┼──────────┼──────────┼──────────┤
      │ departments            │ all auth │ admin    │ admin    │
      │ sections               │ all auth │ admin    │ admin    │
      │ students               │ all auth │ admin    │ admin    │
      │ teachers               │ all auth │ admin    │ admin    │
      │ admins                 │ self     │ admin    │ admin    │
      │ subjects               │ all auth │ admin    │ admin    │
      │ teaching_assignments   │ all auth │ admin    │ admin    │
      │ attendance_sessions    │ all auth │ teacher* │ teacher* │
      │ attendance_records     │ all auth │ teacher* │ teacher* │
      └────────────────────────┴──────────┴──────────┴──────────┘
      * teacher writes only allowed if session.teacher_id = auth.uid()
    Sample SQL:
      CREATE OR REPLACE FUNCTION is_admin() RETURNS boolean AS $$
        SELECT EXISTS(SELECT 1 FROM admins WHERE id = auth.uid());
      $$ LANGUAGE sql SECURITY DEFINER;

      DROP POLICY IF EXISTS auth_write ON departments;
      CREATE POLICY admin_write ON departments FOR ALL
        USING (is_admin()) WITH CHECK (is_admin());

      DROP POLICY IF EXISTS auth_write ON attendance_sessions;
      CREATE POLICY teacher_insert_sessions ON attendance_sessions
        FOR INSERT TO authenticated
        WITH CHECK (teacher_id = auth.uid()::text);

  [D2] Column-Level Redaction
    Why   : Teachers shouldn't see other teachers' contact emails.
    How   : Use Postgres views:
      CREATE VIEW teachers_public AS
        SELECT id, full_name, login_code, role, is_active FROM teachers;
      Grant SELECT on teachers_public to authenticated; revoke on teachers.

  [D3] Row-Level Filtering by Ownership
    Why   : Teachers should only see their own assignments' attendance.
    How   : Attendance RLS policy:
      FOR SELECT USING (
        is_admin() OR
        teacher_id = auth.uid()::text
      )

  [D4] Prevent Mass Assignment
    Why   : Client could send role='admin' in insert to elevate privileges.
    How   : Add CHECK constraints:
      ALTER TABLE teachers ADD CONSTRAINT role_check
        CHECK (role IN ('teacher')); -- no 'admin' allowed here
      ALTER TABLE admins ADD CONSTRAINT admin_role_check
        CHECK (role = 'admin');

  [D5] Data Integrity Constraints
    Why   : Prevent invalid data at DB level, not just app level.
    How   : Already have some. Add more:
      - CHECK (year BETWEEN 1 AND 4) on sections
      - CHECK (credit_hours BETWEEN 1 AND 6) on subjects
      - CHECK (slot_count IN (1, 2)) on attendance_sessions
      - CHECK (status IN ('present', 'absent', 'excused')) on records

────────────────────────────────────────────────────────────────────────────────
 12.4 — INPUT VALIDATION & INJECTION PREVENTION
────────────────────────────────────────────────────────────────────────────────

  [I1] SQL Injection
    Status: Supabase uses parameterized queries via the SDK.
            Direct SQL injection is NOT possible through .from().select()
            or .eq() calls. RPC functions also use parameters.
    Risk  : LOW — but ensure no dynamic SQL inside RPC functions.
    Action: Audit every RPC. Confirm no `EXECUTE format(...)` with
            user-controlled strings.

  [I2] NoSQL Injection
    N/A — Postgres, not MongoDB.

  [I3] XSS (Cross-Site Scripting)
    Context: Flutter Web renders to canvas, not HTML — XSS surface is
             tiny. But text still flows through Text widgets.
    Risk  : LOW. Flutter escapes by default.
    Action: Never use HtmlElementView with user content.
            Sanitize any text shown in tooltips / semantics.

  [I4] Server-Side Input Validation
    Why   : Client validation can be bypassed.
    How   : Add CHECK constraints + Edge Function validation.
            Example: mark_attendance RPC already validates date format,
            slot, slot_count. Extend as needed.

  [I5] File Upload Validation
    Why   : Excel import accepts files — could be exploited.
    How   : Already validate:
      - File extension whitelist (.xlsx, .xls, .csv)
      - Row count max 500
      - Field length limits
      - Regex patterns
    Add  :
      - File size limit (reject > 5 MB)
      - MIME type check via file_picker

  [I6] Rate Limiting on RPC / API
    Why   : Prevent abuse (mark 1000 sessions in 1 minute).
    How   : Add Edge Function wrapper or use Cloudflare in front.
            Simple approach: table api_calls (user_id, endpoint, at)
            RPC checks count in last minute < threshold.

  [I7] Reject Duplicate Requests (Idempotency)
    Why   : Network retries could cause double submission.
    How   : Client generates a UUID per action → sends as request_id.
            Server table idempotency_keys(request_id unique, result jsonb).
            If exists → return cached result.

 12.5 — TRANSPORT SECURITY
────────────────────────────────────────────────────────────────────────────────

  [T1] HTTPS Everywhere
    Status: Supabase enforces HTTPS. Flutter Web enforces HTTPS.
    Action: Ensure deployment is HTTPS (Firebase Hosting / Netlify / Vercel).

  [T2] Certificate Pinning (Mobile)
    Why   : MITM attack prevention on public Wi-Fi.
    How   : Add to pubspec: http_certificate_pinning

                     script-src 'self'; style-src 'self' 'unsafe-inline';">

  [T4] HSTS Header (Web)
    How   : Configure on hosting provider (Firebase Hosting / Vercel).

 12.6 — CLIENT-SIDE SECURITY
────────────────────────────────────────────────────────────────────────────────

  [C1] Secure Storage for Session Tokens
    Status: supabase_flutter uses flutter_secure_storage on mobile.
            On Web, uses localStorage (server-side protections required).
    Action: For mobile, confirm secure storage is enabled (default).
            For Web, ensure short session lifetimes + frequent re-auth.

  [C2] Biometric Auth on Mobile
    Why   : Extra layer — even with stolen phone, no access.
    How   : Add local_auth package.
            On login screen, offer "Unlock with fingerprint".
            Store a local flag after first successful login;
            subsequent launches require biometric before showing dashboard.

  [C3] Screenshot Prevention (Android)
    Why   : Teachers' student lists shouldn't be captured by malware.
    How   : Add flag in MainActivity:
            getWindow().setFlags(FLAG_SECURE, FLAG_SECURE);
            Only on admin screens where PII is displayed.

  [C4] Root / Jailbreak Detection
    Why   : Rooted devices can bypass many security controls.
    How   : Add flutter_jailbreak_detection package.
            On app start, if rooted → warn user or refuse to run.
    Note  : Can be bypassed — it's a deterrent, not a wall.

  [C5] Anti-Tampering
    Why   : Prevent re-signed APKs with injected malicious code.
    How   : Play Integrity API (Android) + App Attest (iOS).
            Requires Edge Function to verify the attestation token.

  [C6] Code Obfuscation on Release
    How   : flutter build apk --obfuscate --split-debug-info=./debug-info
            Makes reverse engineering much harder.

  [C7] Debug Mode Disabled in Release
    Status: Automatically done by Flutter (kReleaseMode = true).
            Ensure no assert() checks rely on debug-only code paths.

   SELECT section_id, COUNT(*) FROM students
     WHERE is_active = true GROUP BY section_id;

   -- Attendance % for a student
   SELECT s.full_name,
          COUNT(*) FILTER (WHERE r.status = 'present') AS present,
          COUNT(*) AS total
   FROM students s
   JOIN attendance_records r ON r.student_id = s.id
   WHERE s.id = '<uuid>'
   GROUP BY s.full_name;

   -- Sessions held today
   SELECT * FROM attendance_sessions
     WHERE date = CURRENT_DATE ORDER BY created_at DESC;

G. Glossary
   RLS         Row Level Security — Postgres feature for row-level access
   RPC         Remote Procedure Call — a Postgres function called from client
   Edge Fn     Supabase's serverless functions (Deno runtime)
   Denorm      Denormalized field — duplicated for read performance
   anon key    Supabase public key — safe to expose, RLS protects data
   service key Supabase admin key — MUST stay server-side only
   JWT         JSON Web Token — used for session auth
   BOM         Byte Order Mark — invisible UTF-8 prefix; stripped in CSV parsing
   CRLF / LF   Windows vs Unix line endings
   PKCE        Proof Key for Code Exchange — auth flow needing storage
   TOTP        Time-based One-Time Password — used in 2FA
   CSP         Content Security Policy — browser-level XSS prevention
   HSTS        HTTP Strict Transport Security — forces HTTPS
   MITM        Man-in-the-Middle attack — prevented by cert pinning
   HIBP        Have I Been Pwned — password breach database
