================================================================================
SECTION 1 — PROJECT OVERVIEW
================================================================================
University attendance system with two portals:
  - ADMIN   : Manages departments, sections, teachers, students, subjects,
              assignments, reports, exports
  - TEACHER : Marks attendance, views assigned classes, sees history

Auth model:
  - Admin creates teacher accounts from admin portal
  - System auto-generates a 6-digit login ID + 8-char random password
  - Trick: uses synthetic email `<id>@uniattend.app`
  - Teacher can log in with the 6-digit ID + password
  - Admin can reset any teacher's password via Edge Function

Database tables (Supabase):
  departments, teachers, admins, sections, students, subjects,
  teaching_assignments, attendance_sessions, attendance_records

SECTION 2 — WHY WE MIGRATED FROM FIREBASE TO SUPABASE
================================================================================
Firebase Spark (free) plan limitations:
  - Cloud Functions require Blaze (pay-as-you-go) plan
  - Blaze requires a billing card (not viable for a Pakistani student)
  - Password reset needs server-side Admin SDK → blocked on Spark
  - Firebase also cut free tier reads by 60% in July 2025

Alternatives evaluated:
  - Appwrite: free tier OK, but UI laggy and migration tool crashed
              on nested structures. Rejected.
  - PocketBase: self-hosted only. Requires laptop 24/7. Rejected.
  - Supabase: ✅ CHOSEN.

Supabase Free Tier:
  - 500 MB database
  - 1 GB file storage
  - 50,000 Monthly Active Users
  - 500,000 Edge Function invocations/month
  - Unlimited API requests
  - No credit card required

Estimated time to hit limits (1,200 students, 120 teachers, realistic usage):
  - Database size   : ~10 years
  - Bandwidth       : ~8 years casual / ~1.5 years heavy
  - Edge Functions  : never
  - MAUs            : ~34 years
  - Project pausing : auto-paused after 7 days inactivity (easy to unpause)

SECTION 7 — TABLE SCHEMAS (Supabase = snake_case)
================================================================================
departments          : id(text PK), name, is_active, created_at

teachers             : id(text PK = auth UID), login_code(text unique),
                       full_name, contact_email, auth_email, role,
                       is_active, has_changed_password(bool), created_at

admins               : id(text PK = auth UID), full_name, email, role,
                       is_active, created_at

sections             : id(text PK, e.g. "CS-3A"),
                       department_id→departments,
                       year(int 1-4), name, academic_year,
                       total_students(int), is_active, created_at

students             : id(uuid PK auto), full_name, roll_no,
                       enrollment_id,
                       department_id→departments, section_id→sections,
                       year(int), is_active, created_at,
                       unique(section_id, roll_no)

subjects             : id(text PK, e.g. "CS301"), name, credit_hours(int),
                       department_id→departments, year(int), semester(int),
                       is_active, created_at

teaching_assignments : id(uuid PK auto), teacher_id→teachers,
                       teacher_name, subject_id→subjects, subject_name,
                       section_id→sections, academic_year, semester(int),
                       created_at

attendance_sessions  : id(uuid PK auto), subject_id→subjects, subject_name,
                       section_id→sections, teacher_id→teachers,
                       teacher_name, date(date), slot(text),
                       start_time, end_time,
                       total_students, present_count, absent_count,
                       late_count(int), status(text), created_at,
                       unique(subject_id, section_id, date, slot)

attendance_records   : id(uuid PK auto), session_id→attendance_sessions,
                       student_id→students, student_name, roll_no,
                       status(text: present|absent|late|excused),
                       remarks, marked_at,
                       unique(session_id, student_id)

RLS: every table has auth_read + auth_write policies for authenticated users.

RPC Functions:
  increment_section_students(p_section_id text, p_delta int) → void
  mark_attendance(...) → uuid
    - atomic insert of one session + its records
    - rejects duplicate (subject, section, date, slot)

Triggers:
  trg_auto_confirm_users on auth.users
    - auto-sets email_confirmed_at on every new signup
    - needed because even with "Confirm email" OFF, Supabase leaves
      new signups unconfirmed

Edge Functions:
  reset-teacher-password (Deno)
    - verifies caller is admin
    - generates new 8-char password
    - updates target user via Admin API
    - returns new plaintext password

  fullName           → full_name

  enrollmentId       → enrollment_id
  departmentId       → department_id
  sectionId          → section_id
  isActive           → is_active
  contactEmail       → contact_email
  authEmail          → auth_email
  academicYear       → academic_year
  totalStudents      → total_students
  creditHours        → credit_hours

  teacherName        → teacher_name
  subjectId          → subject_id
  subjectName        → subject_name
  loginCode          → login_code
  hasChangedPassword → has_changed_password

Key API swaps:
  FirebaseAuth.instance.signInWithEmailAndPassword(...)
    → supabase.auth.signInWithPassword(...)
  FirebaseFirestore.instance.collection('x').doc(id).get()
    → supabase.from('x').select().eq('id', id).maybeSingle()
  Firestore .add({...})
    → supabase.from('x').insert({...})
  Firestore .update({...})
    → supabase.from('x').update({...}).eq('id', id)
  Firestore realtime .snapshots()
    → supabase.from('x').stream(primaryKey: ['id'])
  Cloud Function httpsCallable(...)
    → supabase.functions.invoke('name', body: {...})
  User.uid
    → User.id
  Email TLD .local (rejected by Supabase)
    → .app

SECTION 11 — GIT WORKFLOW (PROFESSIONAL)
================================================================================
GOLDEN RULE: Never commit directly to main. Feature branches + PRs.

--- START A NEW FEATURE ---
  git checkout main
  git pull origin main
  git checkout -b feature/short-description

--- BEFORE COMMITTING ---
  flutter analyze
  flutter test

--- COMMIT + PUSH ---
  git add .
  git commit -m "feat: description"
  git push -u origin feature/short-description

--- ON GITHUB ---
  → "Compare & pull request" → title + description
  → Create PR → wait for CI ✅ → Merge → Delete branch

--- SYNC LOCAL ---
  git checkout main
  git pull origin main
  git branch -D feature/short-description

--- RECOVERY COMMANDS ---
  git restore <file>              discard local changes
  git checkout -f main            force switch
  git reset --soft HEAD~1         undo last commit, keep changes
  git branch -D branch-name       force delete branch
  git remote remove origin        remove broken remote
  git remote add origin <URL>     add new remote

--- COMMIT TYPES ---
  feat / fix / chore / docs / refactor / style / test

--- POWERSHELL SPECIFIC ---
  Remove-Item -Recurse -Force <folder>   (cmd: rmdir /s /q <folder>)
  Get-ChildItem -Recurse -Filter *.dart lib | Select-String "pattern"
